# DynamoDB Tables

This document describes the DynamoDB tables used for data storage in the application.

## Overview

Amazon DynamoDB provides NoSQL data storage for connection mappings and chat messages. The application uses two tables with on-demand (PAY_PER_REQUEST) billing.

## Table Summary

| Table Name | Purpose | Partition Key | Sort Key |
|------------|---------|--------------|----------|
| `family-messenger-connections` | WebSocket connection mapping | UserId | connectionId |
| `family-messenger-messages` | Chat message storage | conversationId | timestamp |

---

## Connections Table

**Table Name**: `family-messenger-connections`
**Billing Mode**: PAY_PER_REQUEST (on-demand)
**Region**: us-east-1

### Schema

| Attribute | Type | Key Type | Description |
|-----------|------|----------|-------------|
| UserId | String | Partition Key (PK) | Cognito username (sub claim) |
| connectionId | String | Sort Key (SK) | API Gateway WebSocket connection ID |
| timestamp | Number | Attribute | Connection establishment time (epoch milliseconds) |

### Example Item
```json
{
  "UserId": "9478a478-9081-7018-199b-d5ac8003f775",
  "connectionId": "abc123xyz-def456",
  "timestamp": 1778517000000
}
```

### Access Patterns

#### 1. Get all connections for a user
```python
# Used by message_handler to find recipient's connections
response = connections_table.query(
    KeyConditionExpression=Key('UserId').eq(userId)
)
```

#### 2. Get user for a connection
```python
# Used by connect_handler and message_handler
response = connections_table.scan(
    FilterExpression=Key('connectionId').eq(connectionId)
)
```

#### 3. Delete a connection
```python
# Used by disconnect_handler
connections_table.delete_item(
    Key={
        'UserId': userId,
        'connectionId': connectionId
    }
)
```

### Use Cases
1. **Message Routing**: When sending a message, look up the recipient's connection ID
2. **Multi-Device Support**: Each device creates a separate connection record
3. **Online Status**: A user with connections is considered "online"

## Messages Table

**Table Name**: `family-messenger-messages`
**Billing Mode**: PAY_PER_REQUEST (on-demand)
**Region**: us-east-1

### Schema

| Attribute | Type | Key Type | Description |
|-----------|------|----------|-------------|
| conversationId | String | Partition Key (PK) | Sorted user ID pair (user1#user2) |
| timestamp | Number | Sort Key (SK) | Message time (epoch milliseconds) |
| senderId | String | Attribute | Username of sender |
| message | String | Attribute | Message text content |

### Example Item
```json
{
  "conversationId": "9478a478-9081-7018-199b-d5ac8003f775#2498c418-d031-7049-64d6-89b418a51ae6",
  "timestamp": 1778517000000,
  "senderId": "9478a478-9081-7018-199b-d5ac8003f775",
  "message": "Hello, how are you?"
}
```

### Access Patterns

#### 1. Get messages for a conversation (newest first)
```python
# Used by history_handler
response = messages_table.query(
    KeyConditionExpression=Key('conversationId').eq(conversationId),
    ScanIndexForward=False,  # Descending (newest first)
    Limit=limit
)
```

#### 2. Save a new message
```python
# Used by message_handler
messages_table.put_item(
    Item={
        'conversationId': conversationId,
        'timestamp': int(time.time() * 1000),
        'senderId': senderId,
        'message': text
    }
)
```

### Conversation ID Generation

Conversation IDs are generated by sorting the two user IDs:

```python
def get_conversation_id(user1_id, user2_id):
    sorted_ids = sorted([user1_id, user2_id])
    return f"{sorted_ids[0]}#{sorted_ids[1]}"
```

### Example
```
User A: "user-123"
User B: "user-456"

Both produce: "user-123#user-456" (sorted alphabetically)
```

This ensures both users share the same conversation ID regardless of who initiates.

## Key Design Decisions

### 1. Composite Primary Keys
Both tables use composite primary keys (PK + SK) for efficient queries:
- Connections: Query all connections for a user
- Messages: Query all messages for a conversation (sorted by time)

### 2. On-Demand Billing (PAY_PER_REQUEST)
- No capacity planning needed
- Pays per read/write operation
- Scales automatically with traffic

### 3. Timestamp as Sort Key
Using timestamp as the sort key enables:
- Efficient time-range queries
- Natural ordering of messages
- Easy pagination

### 4. Denormalized Sender Data
The senderId is stored with each message rather than doing a lookup:
- Reduces DynamoDB reads
- Simpler queries
- Message is self-contained

```hcl
  name           = "family-messenger-connections"
  billing_mode   = "PAY_PER_REQUEST"

    type = "S"

  attribute {
    name = "connectionId"
    type = "S"
  }
}
```

```hcl
resource "aws_dynamodb_table" "messages" {
  name           = "family-messenger-messages"
  billing_mode   = "PAY_PER_REQUEST"
  hash_key       = "conversationId"
  range_key      = "timestamp"

  attribute {
    name = "conversationId"
    type = "S"
  }

  attribute {
    name = "timestamp"
    type = "N"
  }
}
```

## Query Performance

### Connections Table
- Query by UserId: O(n) where n = number of user's connections
- Typical: 1-3 connections per user (browser tabs/devices)

### Messages Table
- Query by conversationId: O(n) where n = number of messages
- Limited to 50-100 messages per query
- Sorted by timestamp (natural chat order)

## Future Considerations

### 1. Pagination
Currently limited to 50 messages. Could add cursor-based pagination:
```python
response = messages_table.query(
    KeyConditionExpression=Key('conversationId').eq(conversationId),
    ScanIndexForward=False,
    Limit=limit,
    ExclusiveStartKey=lastEvaluatedKey
)
```

### 2. Global Secondary Index (GSI)
Could add GSI for querying conversations by user:
```
GSI: user-conversations
PK: userId
SK: lastMessageTimestamp
```

### 3. Message Archival
Long-term storage could use DynamoDB TTL + S3 export.
